# MesaRPG — rewrite (Fase R0)

Esqueleto del nuevo stack, construido en paralelo al prototipo existente (`server/`, `display/`, `mobile/`, `admin/`) **sin tocar nada de ahí**. Ver `VISION.md` §3 y `ROADMAP.md` Fase R0 para el porqué de esta elección de arquitectura y de empezar por aquí.

## Qué prueba este slice

Dos cosas, construidas en dos pasadas:

**1. Que el stack funciona de punta a punta** (2026-08-14, primera pasada): tirar un dado.

```
móvil (/roll)  --WS roll-->  backend (FastAPI)  --resuelve + persiste-->  SQLite
                                    |
                                    +--broadcast-->  mesa (/) --> dado 3D con físicas
```

Verificado: pulsar un dado en `/roll` hace que la pestaña de `/` (mesa, conexión WebSocket independiente) reciba el resultado autoritativo del servidor y anime un dado 3D con físicas reales (Rapier) hasta asentarse, con un badge mostrando el resultado.

**2. Que el modelo multi-campaña real funciona** (2026-08-14, segunda pasada): campañas, pilotos y mechs persistidos con datos reales de Battletech (no solo tiradas sueltas), y salas de WebSocket aisladas por campaña.

```
campaña A ──┬── piloto (gunnery/piloting) ──┬── mech (chasis, tonelaje, MP)
            │                                └── 8 localizaciones (HD/CT/LT/RT/LA/RA/LL/RL)
            │                                    con armadura frontal+trasera y estructura
            └── tiradas (rolls) scoped a esta campaña

campaña B ── (todo lo anterior, independiente — su WebSocket nunca ve nada de A)
```

Verificado con un script de extremo a extremo (dos campañas, un piloto, un Atlas AS7-D completo con sus 8 localizaciones): la validación rechaza mechs con localizaciones incompletas/duplicadas, y un listener conectado a la campaña B no recibe nada cuando se tira un dado en la campaña A.

**3. Núcleo de mesa (R1) y combate (R2)** (2026-08-14, tercera pasada): grid hexagonal con elevación real, niebla de guerra por unidad (no por terreno) con fichas fantasma del GM, y motor de combate (to-hit GATOR + localización 2d6 + daño con desborde a estructura + undo). Todo con backend real y tests de extremo a extremo — ver `ROADMAP.md` Fases R1/R2 para el detalle de qué se verificó y qué sigue bloqueado por hardware (visión, NFC, Raspberry Pi) o aplazado a propósito (plugin de sistema, Battle Value, Total Warfare vs Alpha Strike).

**4. UI de GM y cámara de mesa** (2026-08-14, cuarta pasada): ruta `/gm` para crear pilotos/mechs, atacar y deshacer sin necesitar curl. La mesa (`/`) queda fija en vista cenital — es lo que replicaría la cámara real de la mesa física — salvo cuando un mech es destruido, momento en que se abre un inset tipo picture-in-picture con cámara cinemática durante unos segundos (reacción en vivo, no una repetición grabada de verdad).

**5. Vista de jugador y ficha editable** (2026-08-14, quinta pasada): ruta `/player` — un piloto ve su propia ficha (editable: marcar daño en armadura/estructura directamente, como lápiz sobre papel, vía `PATCH /api/mechs/{id}/locations/{location}`), ve solo los enemigos que su LoS alcanza (Fase R1, no todos los mechs a ciegas) y puede atacarlos o tirar sus propios dados. Antes de esto todo pasaba solo por `/gm`.

**6. Ficha editable y mech 3D** (2026-08-14, sexta pasada): `PATCH` para piloto y para cada localización de un mech (marcar daño directamente, como lápiz sobre la hoja de papel) — base necesaria antes de plantearse digitalizar por foto. Prototipo real de mech 3D de bajo poligonaje (`Mech3D.tsx`) sustituyendo el cono genérico: viable y barato, pero la silueta apenas se distingue desde la cámara cenital por defecto — donde sí paga es en vistas anguladas como el inset de repetición, que ahora reutiliza el mismo componente.

**7. Suite de tests + TDD a partir de ahora** (2026-08-14/15, séptima pasada): `backend/tests/` — 42 tests (pytest) cubriendo `hexgrid` (distancia, trazado de línea, LoS), `combat` (to-hit, tabla de localización, daño, desborde a estructura, undo), `units` (niebla de guerra, revelado de fantasmas) y la capa HTTP (`TestClient`, valida wiring de rutas). Cada test usa una SQLite propia en `tmp_path` — nunca toca `data/mesarpg.db`. Ya encontraron un fallo real de test mal planteado (no del código) antes de darse por buenos — ver `git log`/commits de esta fase. **A partir de aquí el desarrollo es TDD**: test que falla primero, código que lo hace pasar después.

```bash
cd rewrite/backend
pip install -r requirements-dev.txt
pytest -q
```

## Cómo correrlo

**Backend** (Python 3.11+, venv propio en `backend/venv`):

```bash
cd rewrite/backend
python -m venv venv
venv/Scripts/activate          # Windows
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8124
```

**Frontend** (Node 20+):

```bash
cd rewrite/frontend
npm install
npm run dev
```

- Mesa (pantalla compartida): http://localhost:5173/ — sin `?campaign=` en la URL, reutiliza la última campaña existente o crea "Campaña de desarrollo" automáticamente (conveniencia de desarrollo, no gestión de campañas real — ver abajo).
- Tirada (vista de jugador): http://localhost:5173/roll
- GM (crear piloto/mech, atacar, deshacer): http://localhost:5173/gm
- Jugador (ficha propia editable, objetivos visibles, atacar, dados): http://localhost:5173/player
- API: http://localhost:8124/api/campaigns, `/api/campaigns/{id}/pilots`, `/api/campaigns/{id}/mechs`, `/api/campaigns/{id}/rolls`

Ambos ya están corriendo en este entorno tras esta sesión — backend en `:8124` (con `--reload`), frontend en `:5173`.

## Qué es una simplificación deliberada (no un bug pendiente)

- **El resultado del dado no está sincronizado con la física visual.** El servidor decide el número (`app/rolls.py`, `secrets.randbelow`) y lo persiste; la animación 3D es cosmética — tumba con un impulso aleatorio, no está forzada a asentarse en la cara correcta. Corregirlo (o aceptarlo como parte del diseño, mostrando el número como overlay y no como lectura de la cara) es una decisión de Fase R3, no de este slice.
- **Los valores de armadura/estructura de un mech se reciben tal cual, no se calculan.** `app/mechs.py` guarda lo que le pasen por localización (como transcribir una hoja de registro real a mano); deliberadamente NO implementa las tablas de construcción de Battletech (estructura interna según tonelaje, etc.) — eso es motor de reglas (Fase R2) y esos números tienen que salir de una fuente de reglas verificada, no improvisarse aquí.
- **No hay UI de gestión de campañas/pilotos/mechs todavía.** Solo API REST, verificada por script. El frontend resuelve una campaña automáticamente para poder probar la mesa sin fricción, pero crear pilotos/mechs hoy es solo `curl`/script — la UI es Fase R4.
- **Visión no integrada aquí.** El pipeline de cámara sigue siendo el del prototipo (`server/`, `frame_processor.py`, ya validado). Este slice no lo toca — se conecta cuando exista el backend de visión detrás de una interfaz (ROADMAP.md Fase R0, tarea de `VisionBackend`).
- **Sin autenticación** — a propósito, sigue fuera de alcance de "¿rinde el stack nuevo?".

## Qué queda pendiente para que esto deje de ser un slice

Ver `ROADMAP.md` §"Hacia una sesión jugable de principio a fin" — con S0, S1 (+ ampliación), S2 (v1 simplificado), S3, S4 y S5 hechos, **una sesión de Battletech se sostiene sola de principio a fin dentro de la app**. Lo que queda (fases R2-R7 en el resto del roadmap) profundiza reglas de combate y espera a hardware, no desbloquea jugabilidad básica.

**8. Módulo de sistema de juego** (2026-08-16, octava pasada): `app/systems.py` + `app/squaregrid.py` — cada campaña se crea asociada a un sistema (BattleTech=hex, D&D 5e=square, sin reglas de D&D todavía, solo el tipo de grid). `/mapeditor` renderiza cajas o hexágonos según el mapa. 70 tests (TDD), verificado en navegador real creando una campaña D&D desde la UI y confirmando que el editor pinta una cuadrícula de verdad.

**9. Hub, unirse, proyectar, colocar fichas** (2026-08-16, novena pasada): `/hub` con tres accesos (Pantalla/GM/Jugador); `/player` permite unirse creando un piloto propio, no solo elegir uno existente; `/mapeditor` separa "cargar un mapa" de "proyectarlo en pantalla" como acciones distintas, y añade un modo de colocación de fichas (click en el mapa, elegir mech, interruptor fantasma). Auditoría encontró y corrigió dos bugs reales: una vista en blanco tras unirse (faltaba un refetch) y un test intermitente en combate (daño de prueba que a veces desbordaba la armadura de la Cabeza).

**10. Terreno real y generación aleatoria de mapas** (2026-08-16, décima pasada): columna `terrain` propia en vez de inferirlo de elevación/`blocks_los` (9 tipos: llanura, colina, bosque, agua, carretera, rocoso, escombros, peligro, edificio); `app/mapgen.py` genera los mismos 7 biomas que el prototipo anterior (llanuras, bosque, río, ciudad, ruinas, desierto, montañas) con un kit compartido de primitivas (cluster/scatter/near/línea) en vez de una función por bioma. Modelos y texturas 100% procedurales (sin pipeline de assets externo, igual que los pips de los dados): árboles y bloques de edificio como geometría Three.js, agua y carretera como `CanvasTexture` dibujadas a mano. 13 tests nuevos (TDD, 83 en total). Auditoría vía API real (sin CDP disponible en esta sesión) encontró y corrigió un bug real: el bioma "ciudad" salía ~90% edificio por un cálculo de cobertura acumulativo entre clusters — corregido para repartir un total fijo, ahora ~45-55% con calles reales.

**11. Pase de diseño UI/UX** (2026-08-16, undécima pasada): tokens de color/tipografía compartidos (`tokens.css`) en vez de hex repetidos a mano en cada `*.css`; `NavBar` persistente entre mesa/GM/editor de mapas (deliberadamente no en `/player`/`/roll`, que son de un único jugador con enlace ya cargado); `/player` y `/roll` con inputs a 16px (evita el zoom de iOS) y objetivos táctiles de ≥38px; estados de error/carga visibles (`.error-banner`/`.loading`) en las 4 vistas que llaman a la API con datos de campaña; formulario de mech en `/gm` reordenado en 3 pasos con encabezado en vez de un muro de inputs.

**12. Proyección en tiempo real, ciudades coherentes, texturas HD** (2026-08-16, duodécima pasada): el usuario probó en vivo y encontró que "Proyectar en pantalla" no era realmente en tiempo real — arreglado con TDD (`test_setting_active_map_broadcasts_to_table_over_websocket`, rojo primero) retransmitiendo `active_map_changed` por WebSocket y haciendo que `useMapId` acepte un `liveMapId` que sobreescribe el mapa activo al vuelo en `/` y `/player`, sin recargar. El bioma "ciudad" generaba edificios sin ninguna calle para llegar — `_city()` traza ahora calles antes de sembrar los bloques de edificios junto a ellas (`_cluster` gana `force_seed`/`protect`), verificado por TDD que al menos una parte de los edificios toca una calle. Las 9 texturas de terreno pasan de color plano/128px a `CanvasTexture` procedurales de 512px con 3 variantes por tipo elegidas por hash determinista de coordenadas (no aleatorio en cada render). Primer intento de orientar las carreteras rotando su textura — sin navegador para comprobarlo, resultó insuficiente (ver pasada 13).

**13. Carreteras coherentes de verdad, mapas por ancho x alto, edificios derruidos/en pie** (2026-08-16, decimotercera pasada): el usuario probó otra vez y encontró dos problemas reales más — "sigues haciendo clusters de edificio, sin carreteras" (un bug real: `_near` de escombros no respetaba `protect` y podía comerse hasta un 20% de las calles recién trazadas, corregido) y "las lineas de las carreteras no tienen ninguna coherencia" (la rotación de textura de la pasada 12 solo tenía 3 orientaciones posibles y no podía representar una curva/cruce — sustituida por un enfoque correcto por construcción: cada casilla calcula el ángulo real hacia cada vecino que también es carretera y pinta marcas circulares — sin orientación propia, sin ambigüedad de rotación posible — a lo largo de esos ángulos exactos, así que dos casillas vecinas siempre se encuentran en el borde compartido). Los mapas se crean ahora por `width`/`height` en vez de `radius` (`_hex_rect`/`_square_rect`, y `_span_endpoints()` para "un punto en el borde" sin asumir que `(0,0)` es el centro). Los edificios ganan 5 aspectos en vez de 3 genéricos — 3 en pie (con tragaluces y aire acondicionado en la azotea, ya que la cámara de esta app es cenital fija y unas ventanas laterales nunca se verían) y 2 derruidos (silueta rota con escombros, no una caja limpia) — compartidos entre textura y modelo 3D para que nunca se contradigan. 86 tests de backend, build de frontend limpio.

**14. Carreteras de un solo ancho y discontinuas, más biomas, iniciativa/ronda de Battletech** (2026-08-16, decimocuarta pasada): el usuario probó otra vez — las marcas circulares de la pasada 13 aún dejaban "blobs" de 4-5 casillas de carretera en vez de un solo ancho. Causa real encontrada: dos líneas de carretera diagonales en un grid hexagonal se entrelazan justo donde se cruzan (sus "escalones" quedan mutuamente adyacentes, no solo tocándose en un punto) — sustituido el cruce por una calle secundaria corta que se ramifica en una única dirección hexagonal pura desde la calle principal, comprobando en cada paso que no toca la red de calles existente en más de un sitio. Las marcas pasan de puntos a líneas discontinuas de verdad (el trazo más largo que el hueco, como se pidió), construidas como quads de vértices explícitos — sin rotación de objeto en ningún sitio, así que no hay convención de signo que se pueda equivocar. Investigado el juego real (no solo el prototipo antiguo) vía las reglas de BattleMech Manual y el catálogo de mapsheets oficiales: se añaden 4 biomas que faltaban — Pantano, Lago, Ártico y Volcánico (11 en total) — con 2 tipos de terreno nuevos (pantano, nieve). Por último, arranca S2 del roadmap: iniciativa/ronda de Battletech v1 simplificada — investigado el orden real de fase de Total Warfare antes de escribir código, pero sin las 5 fases completas (esta app no tiene ningún concepto de "bando", que la iniciativa de equipo real necesitaría) — tira 2d6 por ronda y lleva la cuenta de qué pilotos ya se activaron, visible en mesa/GM/jugador, sin bloquear acciones fuera de turno. 99 tests de backend (TDD en los tres frentes), build de frontend limpio. De paso, corregidos dos tests intermitentes preexistentes de combate (gunnery 0 no garantiza impacto — un 2 natural falla siempre por regla).

**15. Facciones — jugador/enemigo/NPC** (2026-08-16, decimoquinta pasada): pedido directo del usuario justo después de que la pasada 14 dejara anotado que la app no tenía ningún concepto de bando. `pilots.faction` (tres valores, `player` por defecto, rechazo 422 si no es uno de los tres); `units` hereda la facción de su piloto al leerse (`LEFT JOIN`) para que el mapa pueda colorear cada ficha sin una llamada extra a la API. `/gm` gana un selector de facción al crear un piloto (los jugadores que se unen desde `/player` no lo tienen — siguen siendo siempre `player`); las fichas en mesa y en el editor de mapas pasan de un color por hash de `pilot_id` sin significado a turquesa/rojo/ámbar por facción real. Deliberadamente no se ha tocado todavía la iniciativa de la pasada 14 para hacerla de verdad por bando — esto es la base de datos que lo permitiría cuando se pida, no un rehecho de `turns.py` de golpe. 110 tests de backend (TDD), build de frontend limpio. De paso, un test intermitente más del bioma ártico (nieve podía caer justo al 50% con el rango de clusters anterior) ajustado y verificado estable en 15 ejecuciones.

**16. Iniciativa de verdad por bando, más un modo individual seleccionable** (2026-08-16, decimosexta pasada): el usuario preguntó si con 5 jugadores y 3 enemigos de verdad solo se tiran 2 iniciativas, y pidió confirmarlo bien porque sonaba raro — investigado a fondo con varias fuentes independientes (no reconfirmado de memoria): sí, es la regla real. Pedido inmediato después: un segundo modo, seleccionable por el GM, donde tira cada piloto por separado (con 5 jugadores y 3 enemigos, 8 tiradas). `campaigns.initiative_mode` (`team`/`individual`); `bt_round_rolls` sustituye la tirada única de la pasada 14 — una fila por tirada, de facción o de piloto según el modo; en modo equipos los NPC nunca tiran (no combaten) y los empates se re-tiran de verdad (verificado mockeando la tirada en el test); en modo individual las tiradas salen ordenadas de menor a mayor (menor tirada actúa primero). Selector de modo en `/gm`, tiradas listadas con nombre/facción en las tres vistas vía un formateador compartido (`src/rounds.ts`). 120 tests de backend (TDD), build de frontend limpio. Auditado extremo a extremo reproduciendo el escenario exacto del usuario vía API real: modo equipos → 2 tiradas, modo individual → 8 tiradas, NPC excluido en ambos.

**17. Armas y equipo real** (2026-08-16, decimoséptima pasada): el usuario preguntó si era hora de meter las reglas de Battletech de verdad. Antes de ponerse a ello, se detectó que `damage` en un ataque siempre había sido un número que el GM escribía a mano — sin ningún arma real detrás — y que calor/críticos/Battle Value dependen todos de que las armas existan primero, así que se hizo eso primero, con permiso explícito del usuario ("tu mandas"). `app/weapons.py`: catálogo de las 16 armas estándar de la Esfera Interior, cada una verificada individualmente contra Sarna.net (no de memoria) — láseres, PPC, ametralladora, los 4 autocañones, SRM/LRM de todos los tamaños. `mech_weapons`: loadout por mech y localización, con munición inicializada desde el catálogo para las armas que la usan; disparar consume una ronda tanto si acierta como si falla. `combat.resolve_attack` acepta ahora `weapon_id` (busca daño en el catálogo, descuenta munición, rechaza si no queda) además del `damage` manual de siempre — compatibilidad completa, nada de lo existente se rompió. `/gm` gana una sección "Armamento" para montar/quitar armas en cualquier mech; el formulario de ataque en `/gm` y `/player` pasa de "escribe un número" a elegir un arma real del atacante, con la munición restante visible. 142 tests de backend (TDD en los tres frentes: catálogo, loadout, resolución de ataque), build de frontend limpio. Auditado extremo a extremo vía API real: arma montada con la munición inicial correcta, disparo aplica exactamente el daño del catálogo (AC/20 → 20) y descuenta una ronda. El calor se guarda por arma pero deliberadamente no se aplica a nada todavía — es el siguiente paso natural, no un descuido.

**18. Calor sobre to-hit** (2026-08-16, decimoctava pasada): siguiente paso natural pedido justo después de las armas. La tabla de calor tiene peor verificación que el resto de `combat.py` — varias fuentes secundarias daban umbrales distintos para reducción de movimiento/apagado/explosión de munición, así que solo se implementa la columna de to-hit (0-7→+0, 8-12→+1, 13-16→+2, 17-23→+3, 24+→+4), documentado explícitamente como más débil que el resto del archivo, y el resto de efectos (movimiento, apagado, explosión de munición) se quedan deliberadamente fuera por no tener una fuente en la que confiar del todo. `mechs.heat_sinks`/`heat_current` (nuevas columnas, 10 disipadores por defecto); cada disparo con arma real aplica la penalización según el calor QUE YA TENÍA el atacante antes de ese disparo, y luego le suma el calor del arma. El calor se disipa al empezar una ronda nueva (`turns.start_round` llama a `mechs.dissipate_all_heat` para toda la campaña) — el mapeo más cercano disponible a la Fase de Calor real sin construir una máquina de fases completa. Frontend: campo de disipadores al crear un mech, calor visible en la lista de mechs, en el selector de atacante y en la ficha propia del jugador. 151 tests de backend (TDD en mechs/combat/turns/api), build de frontend limpio, estable en 2 ejecuciones completas repetidas. Auditado extremo a extremo vía API real: dos disparos seguidos de una PPC suben el target number de 4 a 5 por el calor acumulado, y una ronda nueva lo disipa correctamente (20 − 10 disipadores = 10).

**19. Auditoría contra fuentes oficiales (PDF + ficha de referencia Total Warfare)** (2026-08-15, decimonovena pasada): el usuario puso el rulebook oficial CAT3500D en `rewrite/`, y más tarde una ficha de referencia de Total Warfare (PDF, con fuentes Type3 sin CMap Unicode — renderizada a imagen y leída visualmente en vez de extracción de texto) y el manual BattleMech (txt). Se cotejó cada número ya implementado: catálogo de armas, tabla de localización de impacto y modificadores de movimiento/rango del atacante — los tres confirmados exactos, sin cambios. Bug real encontrado y corregido: `combat.target_movement_mod()` se quedaba fijo en +4 para cualquier objetivo movido más de 9 hexágonos, cuando la tabla oficial exige +5 entre 18-24 y +6 a partir de 25 — corregido con TDD, 151 tests estables en 2 pasadas. La advertencia de "verificación más débil" del calor sobre to-hit (pasada 18) queda retirada del docstring de `combat.py`: los umbrales están ahora confirmados exactos contra la fuente oficial. Quedan documentados como fiablemente disponibles pero sin implementar: resto de la Heat Scale (reducción de movimiento, apagado, explosión de munición), calor generado por moverse, Cluster Hits Table completa, tabla de críticos, modificadores de terreno — ver `ROADMAP.md` Fase R2 para el detalle completo.

**20. Hub en tiempo real (Fase 1 de "suite jugable")** (2026-08-15, vigésima pasada): el usuario aclaró el uso real de la app — una mesa física, nunca campañas simultáneas, todos los dispositivos parten de `/hub` con solo el botón GM activo. Hasta ahora, para que "Pantalla"/"Jugador" se activaran en los demás dispositivos hacía falta que alguien les pasara un enlace con `?campaign=` ya puesto — sin ninguna propagación real entre dispositivos. Tabla nueva `table_session` (fila única, coherente con "nunca hay partidas concurrentes") + `app/table_session.py`; canal WebSocket nuevo y deliberadamente separado del `ConnectionManager` por-campaña existente, `HubManager` en `app/ws.py` — transporta solo la señal meta "qué campaña está activa", nunca estado de juego, así que no reintroduce el problema que hizo eliminar el canal compartido original. `POST /api/table-session/activate` persiste y hace broadcast por `/ws/hub`; `GET /api/table-session` da el estado inicial a un dispositivo que se conecta más tarde. Gotcha real de enrutado encontrado y evitado: `/ws/hub` tiene que registrarse ANTES que `/ws/{campaign_id}` en `main.py`, porque ese patrón de ruta no lleva conversor de tipo a nivel de Starlette — si se registrara después, "/ws/hub" intentaría matchear ahí primero y fallaría la conversión a `int`. `CampaignsView.tsx` activa la sesión de mesa al elegir/crear campaña (best-effort, no bloquea al GM si falla); `HubView.tsx` usa el nuevo `useHubSocket()` en vez de depender solo del query param de su propia URL — el query param sigue funcionando como override manual. 158 tests de backend (TDD, incluida una guarda explícita anti-regresión de que el canal del hub no se mezcla con las rooms por campaña), build de frontend limpio. Verificado extremo a extremo con un cliente WebSocket real: conectar a `/ws/hub`, activar una campaña por API, y el mensaje llega en vivo; sin herramienta de navegador/CDP disponible en esta sesión para abrir dos pestañas reales, así que la verificación visual en dos dispositivos físicos queda pendiente de que el usuario la pruebe.

**21. Reconexión del hub + "Terminar sesión"** (2026-08-15, vigesimoprimera pasada): el usuario probó la pasada 20 en real y reportó que los dispositivos parados en `/hub` no se actualizaban. Se instaló Playwright con Chromium real (antes solo se había verificado con un cliente WebSocket crudo) para poder reproducirlo — en una pestaña `/hub` recién abierta el flujo SÍ funcionaba de punta a punta, así que el sospechoso principal pasó a ser lo que un `/hub` recién abierto no cubre: un móvil parado ahí un rato con la pantalla bloqueada o en segundo plano, donde los navegadores móviles suelen suspender el WebSocket sin avisar y `useHubSocket` no tenía ninguna reconexión. Añadido: reconexión automática cada 2s mientras el componente siga montado si el socket se cierra, y un refresco del estado (`GET /api/table-session` + reconectar si hace falta) al recuperar visibilidad de la pestaña (`visibilitychange`) — así un móvil que vuelve de segundo plano se pone al día aunque el socket llevara tiempo muerto en silencio.
